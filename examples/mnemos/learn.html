mnemos: architecture guide

Built from the project's own tests on 2026-11-11.

Mnemos gives an LLM agent a memory that lasts across conversations. One facade, MemoryEngine, stores what was said (episodes) and short facts distilled from it, and finds them again by meaning and by how recent they are. The conversation loop, the API and the MCP server all go through that facade, and the storage underneath can be Postgres, Qdrant or Neo4j.

In the 63 tests, the time goes mostly to computing text embeddings: one function, the local embedding model, holds about 83% of the traced time, and it only runs in two tests. Two tests fail, both about fact decay. 68 of 148 public functions are never run by a test, among them the real Groq and Anthropic clients, most of the Neo4j backend and the command-line entry points.

Architecture

Four layers. The agent layer (agent/conversation.py) runs one chat turn. The memory layer (memory/) holds the engine, retrieval scoring, fact extraction, procedural memory and reflection. The storage layer (storage/) is one abstract interface with three backends. The entry points (api/, cli/, mcp_server.py) build these pieces and call down. Callers never touch storage directly: engine.py:19-24 says MemoryEngine is the single entry point, so a new backend or memory type is added behind it.

How a request moves

One chat turn, in ConversationManager.handle_message (agent/conversation.py:43-82):

  • Score the previous turn's retrieval strategy, using this message as feedback (conversation.py:48).
  • Pick a strategy for this turn: a pair of similarity and recency weights (conversation.py:49, memory/procedural.py:60-81).
  • Recall memories for the message (conversation.py:51 calls engine.py:81-107). The engine embeds the query, asks the storage backend for nearest episodes and facts, scores them, and keeps the top few (memory/retrieval.py:65-99).
  • Build the system prompt from what was recalled, then call the LLM (conversation.py:54-59).
  • Store the user message and the reply as two episodes, each with an embedding (conversation.py:61-64, engine.py:37-60).
  • Mark this turn's strategy as waiting for feedback (conversation.py:65).
  • Every n turns, send the turn to the LLM with a record_facts tool and store the facts it returns, skipping near-duplicates (conversation.py:114-138, memory/extraction.py:42-100).

State and data

  • Episodes and facts live in the chosen storage backend: Postgres, an embedded Qdrant directory, or Neo4j (storage/factory.py:10-36).
  • Procedural memory and the reflection log always live in Postgres, whichever backend you pick (storage/base.py class docstring, api/deps.py:23).
  • Postgres is opened per call. Qdrant and Neo4j are kept as one shared instance per process in a module-level dict (storage/factory.py:7, 19-35). That dict is lost on restart; the data is not.
  • The API loads the embedding model, the LLM clients and the storage backend once at startup, not per request (api/main.py:14-27).
  • A new MemoryEngine is built for every request around those shared parts (api/deps.py:12-16).

Patterns and gotchas

  • Facade: MemoryEngine hides storage, embeddings and retrieval from every caller (memory/engine.py:19).
  • Strategy by feedback: procedural memory picks between three weightings (memory/procedural.py:15-19). It is epsilon-greedy, so some turns pick at random (procedural.py:67-69). An unseen strategy starts at a neutral 0.5 (procedural.py:74-75).
  • Reading changes data: recall calls reinforce_fact on every fact it returns (memory/engine.py:98-106). A recall is also a write.
  • Facts are ranked on similarity alone, with no recency term (memory/retrieval.py:38-42). Only episodes get the recency boost (retrieval.py:25).
  • The duplicate check compares a new fact to the single nearest existing fact (memory/extraction.py:95). A near-duplicate that is second-nearest would pass.
  • Extraction is skipped on most turns when extraction_every_n_turns is above 1 (conversation.py:123-128). Facts can lag behind what was said.
  • Decay is measured from last_reinforced_at (memory/reflection.py:10). It reads the clock of the machine running the code, and the timestamp is written by the database (db/models.py:97). If the two clocks differ, a fresh fact can look like it is from the future.
  • Closing an engine clears the shared backend cache for the whole process (memory/engine.py:121-137). Another engine in the same process gets a fresh backend next time.

Reading order

  • memory/engine.py: the facade. Everything else hangs off it.
  • agent/conversation.py: one chat turn, top to bottom.
  • memory/retrieval.py: how a memory gets its score.
  • storage/base.py, then storage/postgres_backend.py: the interface, then the simplest backend.
  • memory/extraction.py: how a turn becomes facts.
  • memory/reflection.py: merge, decay and forget over time.
  • memory/procedural.py: how the system learns which weighting works.
  • api/main.py and api/deps.py: how it is wired up when served.

Then run /flow <test name> on one test to watch the calls happen.

What the tests cover

  • The two failing tests are decay forgets fact below confidence threshold and decay reduces confidence without forgetting, both in tests/unit/test_reflection.py. Both expect one fact to decay and none did. The Docker VM I ran them in was about 5 seconds ahead of this machine, which fits the clock gotcha above (inferred, not confirmed on your machine).
  • Tests use mock embeddings and a mock LLM almost everywhere. The real Groq and Anthropic clients are never run by a test.
  • Most of the Neo4j backend, the CLI commands, the MCP server and the benchmark scripts are not run by any test. Untested here does not mean broken.
