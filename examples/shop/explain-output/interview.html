shop: architecture walkthrough

Built from the project's own tests on 2026-11-11.

The shop is a checkout service split into four small modules: orders coordinates, stock decides whether an order is allowed, pricing computes the total, and catalog holds the prices. mailer produces the receipt. Each module does one job and orders is the only one that calls the others.

The tests cover every module. They show one clear hot spot: the price lookup takes almost all of the running time.

Talking points

  • Walk the main flow: place an order, reserve stock, price the cart, send a receipt. Use the use case "small order gets a receipt".
  • Show the diagram: one coordinator, three helpers, one lookup at the bottom. Point at catalog, the dark box.
  • Slowest part: the price lookup, nearly all of the time. Sample answer (replace with yours): I would cache prices, because they change rarely.
  • Why this split: sample answer (replace with yours): each module can be tested on its own, which is why there are small, fast tests.
  • Not tested: behavior with many customers at once. Sample answer (replace with yours): stock.reserve would need a lock or a database transaction.
  • Question to answer yourself: what would you change first if this had to handle a hundred orders a second?
